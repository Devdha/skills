# zen-brainstorm — 자율 실행 계약서 만들기

## 개요

대화형 브레인스토밍으로 설계를 수렴시킨다. 일반 브레인스토밍과 다른 점 두 가지:

1. 산출물이 **자율 실행 계약서**다 — 이후 단계(구현·리뷰 finding 판단·최종 검증)가 사용자 개입 없이 이 문서만으로 진행 가능해야 완료다.
2. 산출물이 **팀 공유용 의사결정 로그**다 — 왜 이 태스크를 하는지, 왜 이 방식을 골랐는지가 문서에 남고, 승인 시 Notion 기획 DB에 적립되어 팀이 결정 과정을 따라올 수 있다.

기능적으로 "된다/안 된다"보다 **이 의사결정의 근거를 팀과 맞출 수 있는가**가 리뷰 병목이다. 인터뷰 트랙은 그 근거를 설계 시점에 강제로 확보한다.

## 진행 방식

1. **컨텍스트 선수집**: 관련 코드 탐색(구조, 유사 구현 선례), 근거 데이터(프로젝트에 analytics/insight 계열 스킬이 있으면 활용), 기존 문서·컨벤션.
2. **인터뷰 트랙 (필수 — 순서대로, 답이 §1에 적립된다)**:
   1. **계기**: 이 태스크를 왜 지금 하게 되었는가? 출처를 명시한다 — 사용자 제보, 데이터/지표, 리뷰 지적, 팀 논의, 직감. 사용자의 첫 요청에 이미 담겨 있으면 재질문하지 않고 확인만 한다.
   2. **유형 분기**:
      - **버그** → 설계 전에 **라이트 재현 검증**: 코드 추적이나 로컬 재현으로 실제로 재현되는지 가볍게 확인하고, 재현 스텝·원인 후보를 기록한다 (전체 검증 하네스가 아니다 — 수 분 수준). **재현이 안 되면 설계로 넘어가지 않고 보고한다.**
      - **피쳐/개선** → **고객 가치 가설**: 어떤 사용자가, 어떤 상황에서, 무엇이 좋아지는가를 한 문장으로 확보한다. 가치가 흐릿하면 질문만 반복하지 말고 **유저가 가치를 느낄 방향의 구체안을 제시**해 반응을 얻는다.
   3. **대안 비교**: 접근이 갈리는 지점마다 대안 2~3개 + 트레이드오프를 제시하고 추천안을 앞세운다. 최종적으로 **"다른 방법 대비 왜 이것인가"**에 답할 수 있어야 한다 — 선택한 안과 기각한 안의 이유가 §1.3에 남는다.
3. **질문은 한 번에 하나.** 가능하면 선택지 2~4개 + 추천안 명시. 사용자가 이미 결정한 사항은 재질문하지 않는다.
4. 수렴하면 설계를 200~300단어 섹션으로 나눠 제시하고 섹션마다 확인받는다.

## design.md 필수 섹션 (하나라도 비면 완료가 아니다)

```markdown
# {태스크 이름} 설계

## 0. 메타
- 브랜치: {프로젝트 컨벤션에 따른 브랜치명 — 여기서 확정한다. run_dir slug의 기준}
- base 브랜치: {PR이 향할 브랜치}
- 리뷰 하네스: {zen Phase 0에서 선택된 스킬명}
- 검증 유형: 화면 | 로직(실환경) | 화면+로직 | N/A — {N/A는 실행 표면 자체가 없는 태스크(문서·주석·설정)만. 사유 명시}
- 화면 뷰포트: PC(1440x900) 기본. **변경이 반응형 레이아웃·모바일 전용 UI·터치 인터랙션을 건드리면 모바일(390x844) 필수 포함** — 해당 시나리오에 뷰포트 표기. {검증 유형에 화면이 없으면 이 행은 생략}
- 기획 페이지: {Notion URL — 승인 시 기록}

## 1. 배경과 의사결정
- 1.1 계기: {무엇이 이 태스크를 촉발했나 — 출처(제보/데이터/리뷰/논의) 포함}
- 1.2 (버그) 재현 확인: {재현 스텝, 재현 여부, 원인 후보} | (피쳐) 고객 가치 가설: {누가, 어떤 상황에서, 무엇이 좋아지나}
- 1.3 검토한 대안과 선택 근거:
  | 대안 | 장점 | 단점 | 판정 |
  |---|---|---|---|
  {선택안과 기각안 모두, 기각 이유 명시}

## 2. 구현 스펙
변경 대상, 동작, 엣지 케이스. **제외 범위를 명시**한다.
데이터/스키마 변경이 있으면 마이그레이션·롤백 방법도 명시한다.

## 3. 검증 시나리오
§0 검증 유형이 N/A면 이 섹션은 `N/A (사유)`로 표기하고 §5에 대체 증거(테스트, CLI 출력, 로그)를 정의한다. 시나리오마다 유형별 4요소 강제:

### 시나리오 1: {한 줄 이름} [화면]
- 진입: (URL/화면, 로그인 상태, 필요한 픽스처)
- 액션: (수행할 조작)
- 기대: (화면에서 확인할 것 — 구체적으로)
- 캡처: (스크린샷 찍을 상태, 뷰포트: PC | 모바일 | 둘 다, 마스킹 대상 있으면 명시)

### 시나리오 2: {한 줄 이름} [로직]
- 준비: (기동할 스택, 필요한 픽스처/시드 데이터)
- 실행: (실제로 날릴 호출·명령 — 엔드포인트/페이로드/CLI를 구체적으로)
- 기대: (응답·상태 변화 — 상태 코드, 응답 필드 값, DB/로그 변화를 구체적 값으로)
- 증거: (캡처할 것 — 요청/응답 본문, 로그 라인, DB 스냅샷)

## 4. 리뷰 finding 판단 기준
- 의도적 트레이드오프: 리뷰에서 지적돼도 기각할 결정들과 이유 (§1.3의 기각안 포함)
- 스코프 제외: 이번 PR에서 다루지 않는 것
- 기각 불가(반드시 반영): 보안, 데이터 손상, 크래시 등

## 5. 완료 기준
테스트/빌드/검증 통과 조건.
```

저장 위치: `~/.zen/runs/{repo}/{branch-slug}/design.md`

## 종료 게이트

설계 제시 중의 섹션별 확인("여기까지 괜찮나요?")은 **초안 피드백일 뿐 실행 승인이 아니다.**

**승인 브리핑 (게이트 질문 직전, 필수)**: 섹션별 확인은 대화에 흩어져 있으므로, 승인 시점에 사용자가 **이 브리핑만 보고 태스크 전체와 진행 방향을 파악할 수 있어야 한다.** design.md에서 추출해 한 화면으로 제시한다 (새 정보 금지 — 브리핑에 쓸 내용이 문서에 없으면 문서가 미완성인 것이다):

```markdown
## 승인 브리핑
- **무엇을**: {태스크 한 줄}
- **왜 지금**: {계기 + 출처 (§1.1)}
- **가치/재현**: {피쳐: 누가·언제·무엇이 좋아지나 | 버그: 재현 확인 결과} (§1.2)
- **선택한 접근**: {선택안 한 줄} — 기각: {기각안: 이유 한 줄씩} (§1.3)
- **바꾸는 것 / 안 바꾸는 것**: {변경 대상 요약} / {제외 범위} (§2)
- **어떻게 확인하나**: {검증 시나리오 이름 나열 | N/A + 대체 증거} (§3, §5)
- **리뷰에서 알아서 판단할 것**: {§4 트레이드오프·스코프 제외 요약 — 이 기준으로 finding을 자율 처리한다}
- **이후 진행**: 구현 → PR → 리뷰 수렴({하네스명}, 최대 3라운드) → 최종 검증({검증 유형}) → 완료 보고 (승인 후 무질문)
```

브리핑 제시 후 반드시 별도로 묻는다: **"이 설계대로 구현 → PR → 리뷰 수렴 → 최종 검증까지 자율 진행합니다. 시작할까요?"**

**승인 판정**: 이 게이트 질문에 대한 무조건적 긍정 응답만 승인으로 인정한다. 조건이 붙은 응답("~만 고치고 진행해")은 조건을 design.md에 반영한 뒤 게이트 질문을 다시 던진다. 감상("좋아 보이네")이나 질문이 섞인 응답은 승인이 아니다. 애매하면 승인으로 간주하지 않고 재확인한다.

**승인 직후 — Notion 기획 적립 (zen 파이프라인의 게이트)**:

1. `~/.zen/config.json`의 `notion_planning_db`에 **태스크당 1페이지**를 생성한다.
   - 속성: `태스크 이름`(title), `유형`(버그/피쳐/개선/기타), `상태`=`설계 승인`, `레포`(slug), `승인일`(오늘). `PR` 열은 비워둔다 (zen Phase 3에서 기입).
   - 본문은 아래 **페이지 작성 규칙**을 따른다.

   **페이지 작성 규칙** (사람이 읽는 공유물 — design.md의 미러가 아니다):

   - **독자 계약**: 팀원이 **3분 안에 훑고 "왜 이렇게 결정했는지" 설명할 수 있어야 한다.** 이 기준으로 모든 분량·구조를 결정한다.
   - **구조** (Notion 네이티브 블록, 위에서부터 이 순서로):
     1. 📌 콜아웃 — 한 줄 요약 (무엇을 + 왜, 2문장 이내)
     2. 승인 브리핑 (종료 게이트에서 제시한 8줄 그대로)
     3. 구분선
     4. **왜 이 결정인가** — 계기 1~2줄, 가치/재현 1~2줄, 대안 비교 표 (§1.3 기반, 선택안 굵게)
     5. **무엇을 만드나** — 불릿 3~5개, 제외 범위 포함 (§2 요약)
     6. **어떻게 확인하나** — 검증 시나리오 이름 나열 (§3)
     7. ▸ 토글: 브레인스토밍 Q&A·방향 전환 전체 로그
     8. ▸ 토글: 리뷰 판단 기준 (§4 전문)
     9. 푸터 — design.md 파일 경로
   - **상세·원문은 전부 토글로 접는다** — 토글 밖 본문은 요약만. 이것이 간결함과 기록 완전성을 동시에 지키는 장치다.
   - **문장 규칙**: 개조식. 한 불릿 = 한 정보, 두 줄 금지. 결론 먼저, 근거 뒤. 코드·경로·API는 code 서식. 이모지는 콜아웃 1개 외 사용 금지.
   - **금지**: design.md 통째 복붙, 대화 로그 시간순 나열, 헤더 남발, 수식어로 늘린 문장.
   - **게시 전 셀프체크** — 하나라도 아니오면 고친 뒤 게시한다: ① 3분 내 파악 가능한가 ② 토글 밖에 두 줄 넘는 문단이 없는가 ③ 모든 표·불릿이 중복 없는 새 정보인가
2. 생성된 URL을 design.md §0 `기획 페이지`에 기입하고 zen에 전달한다 (`state.planning_page_url`).
3. **생성 실패(Notion 연동 부재·권한)면 zen 파이프라인에서는 Phase 2로 진입하지 않고 예외 5로 중단·보고한다.** 단독 호출(zen 밖)이고 `notion_planning_db`가 없으면 적립을 스킵할 수 있다 — 스킵 사실을 사용자에게 고지한다.

승인을 받으면 종료하고 zen 파이프라인이 이어받는다 (zen이 design.md 해시를 기록하며, 이후 문서는 read-only). 승인 전에는 어떤 구현도 시작하지 않는다.

## 흔한 실수

- 검증 시나리오를 "동작 확인"처럼 추상적으로 작성 → 재현 불가능. 유형별 4요소(화면: 진입/액션/기대/캡처, 로직: 준비/실행/기대/증거)를 강제한다.
- **화면 없는 로직 태스크를 N/A로 분류** → 금지. N/A는 실행 표면이 없는 태스크뿐이다. API·배치·데이터 처리는 로직 시나리오로 실환경 재현을 정의한다.
- **반응형·모바일 UI 변경인데 PC 시나리오만 작성** → 모바일 뷰포트 시나리오를 포함한다.
- §4 판단 기준 생략 → Phase 3/4에서 suggestion 처리가 임의적이 된다. 브레인스토밍 중 나온 트레이드오프 결정을 그때그때 §4에 적립한다.
- **계기·대안 비교 없이 구현 스펙부터 설계** → §1이 비면 게이트 통과 불가. 리뷰에서 "왜 이 방식인가"에 답할 근거가 사라진다.
- **버그를 재현 확인 없이 수정 설계** → 금지. 재현이 안 되면 설계 대신 보고한다.
- **피쳐의 고객 가치를 사용자에게 캐묻기만 함** → 가치가 흐릿하면 구체적 방향을 제시해서 반응을 얻는 게 이 스킬의 역할이다.
- **승인 브리핑 없이 게이트 질문만 던짐** → 금지. 섹션별 확인 기억에 의존한 승인은 "전체 그림을 파악한 승인"이 아니다.
- 여러 질문을 한 번에 던짐 → 사용자 피로. 하나씩.
- 이미 결정된 사항 재질문 → 대화 기록과 §4에 적립한 결정을 먼저 확인.
- **Notion 적립 실패를 무시하고 승인 처리** → zen 안에서는 게이트다. 예외 5로 중단·보고.
- **Notion 페이지에 design.md를 통째로 복붙하거나 대화 로그를 시간순 나열** → 금지. 토글 밖은 3분 안에 읽히는 요약만, 원문·로그는 토글에 접는다.
