# zen-verification — 최종 검증 (화면 + 로직 실환경 재현)

## 개요

검증 시나리오를 **실제 환경에서 재현**해 PR에 넣을 증거를 만든다. 두 모드:

- **화면 모드**: 실제 브라우저에서 시나리오를 재현하고 스크린샷을 S3에 올려 **PR 바디에 넣을 수 있는 영구 URL**을 만든다.
- **로직 모드**: 로컬 스택을 실제로 띄우고 **실제 API 호출·명령 실행**으로 시나리오를 재현해 요청/응답·로그·DB 상태 변화를 텍스트 증거로 캡처한다.

zen 파이프라인 안에서는 **리뷰 수렴이 끝난 최종 head SHA**에서 실행된다 (zen Phase 5) — 검증한 커밋이 PR head와 일치하는지가 증거의 핵심이다.

**캡처물은 목적이 아니라 증거다.** 기대 결과가 실제로 확인되지 않으면(빈 화면, 로딩만, 다른 화면, 기대와 다른 응답) 실패로 보고한다. 다른 화면·다른 호출의 결과를 증거로 쓰지 않는다. **단위 테스트·mock 호출은 어느 모드에서도 증거가 아니다** — 실제 프로세스에 실제 요청이 나가야 한다.

## 입력

시나리오 목록 (zen design.md §3 형식): 화면 시나리오는 진입/액션/기대/캡처(+뷰포트), 로직 시나리오는 준비/실행/기대/증거. 단독 호출이면 이 형식으로 먼저 정리한 뒤 시작한다.

`{run_dir}` = `~/.zen/runs/{repo}/{branch-slug}/` (slug: 소문자, 영숫자 외 문자는 `-`). 단독 호출로 아직 없으면 생성한다.

## 절차

0. **사전 게이트 (시나리오 실행 전 — 실패 시 예외 5, verify_attempts 미소모)**  
   아래를 통과하지 못하면 시나리오를 돌리지 않는다. 통과 증거를 results 또는 verification/preflight.md에 남긴다.
   1. `~/.zen/projects/{repo}.md`의 **surface 런북** 확인 (web / extension / embed 등). 해당 surface 절이 없으면 프로젝트 문서·기존 e2e에서 찾아 캐시에 추가한 뒤 진행.
   2. **로컬 스택 ready**: base URL `curl` 200(또는 프로젝트 허용 코드). API/프록시가 분리되면 각각 확인.
   3. **인증 경로 ready**: 프로젝트 메모의 mock/test 로그인 또는 env 크리덴셜. **로그인 성공 스모크** (쿠키/세션 또는 `user.id` 존재)를 시나리오 전에 1회 검증.
   4. **아티팩트 ready** (extension/native 앱): 빌드 산출물 존재 + **개발 오리진과 일치하는 빌드 플래그** (예: API base가 localhost). 정적 자산 누락 의심 시 빌드 로그/`ERR_FILE_NOT_FOUND` 확인.
   5. **S3**: `~/.zen/config.json` 존재 여부. 없으면 시나리오는 진행 가능하되 **업로드는 `upload_failed: true`**로 명시 (시나리오 pass와 분리). 버킷/공개 URL이 비어 있으면 추측 업로드 금지.
   6. 런타임 버전(Node 등)이 프로젝트 AGENTS.md 요구와 다르면 **전환 후** 재시도 — 버전 불일치를 제품 버그로 해석하지 않는다.

1. **dev 서버 확보**
   - `~/.zen/projects/{repo}.md`에 기동 명령/base URL 캐시가 있으면 사용. 없으면 package.json scripts와 프로젝트 문서에서 파악하고 캐시에 기록. **base URL이 로컬(localhost/127.0.0.1)이 아니면 검증하지 않고 중단·보고한다** (공유 dev/staging에 픽스처를 남기지 않기 위해).
   - 떠 있는 서버 재사용은 **이번 변경이 반영된 서버임을 확인한 경우에만** (HMR 로그, 변경된 요소 스팟 체크). 확인 불가하거나 다른 브랜치/워킹카피의 서버로 의심되면 재사용하지 말고 **빈 포트에 새로 띄운다** (동시 실행 충돌 방지). 새로 띄우면 백그라운드 실행 + ready 신호 대기.
   - 검증에 사용한 base URL과 **head 커밋 SHA**를 results.json에 기록한다 — 스크린샷이 어느 커밋의 화면인지가 증거의 핵심이다.

2. **브라우저 어댑터 선택 (화면 모드 — 우선순위)**
   1. **프로젝트 기존 e2e/헬퍼** — 레포에 Playwright/Cypress 헬퍼(`open*`, `ensureLoggedIn`, extension launch)가 있으면 **그걸 우선 재사용**한다. zen 전용 스크립트를 새로 쓸 때도 동일 헬퍼를 import한다 (로그인·뷰어 부팅을 재발명하지 않음).
   2. **Playwright(또는 Puppeteer)** — 기본. 스크립트는 `{run_dir}/verification/` **또는** 패키지 `tests/*.zen.spec.ts`에 저장해 재실행 가능하게 남긴다. **미설치면 프로젝트 의존성(package.json/lockfile)을 건드리지 말고** `npx playwright` 또는 scratchpad 별도 디렉토리에 설치해 사용 — 그것도 불가하면 호스트 네이티브로 폴백.
   3. **호스트 네이티브** — 기존 로그인 세션 재활용 등 헤드리스로 곤란할 때만: Claude Code→claude-in-chrome, Codex→browser plugin/Chrome automation, Grok→가용 브라우저 툴.
   - 뷰포트: **PC 1440x900 기본**. §3 시나리오에 모바일이 지정된 경우 **모바일 390x844로도** 캡처 — 가능하면 Playwright 디바이스 프리셋(`devices['iPhone 14']` 등)으로 터치/UA까지 에뮬레이션. 시나리오에 지정되지 않은 뷰포트를 임의로 추가하거나, 모바일 지정 시나리오를 PC 캡처로 대체하지 않는다.
   - extension/MV3: `launchPersistentContext` + `--load-extension` 등 프로젝트 헬퍼 패턴을 따른다. 일반 `page.goto(app)`만으로 extension UI를 검증하지 않는다.

3. **로그인/픽스처**
   - 테스트 계정: `~/.zen/projects/{repo}.md`에 기록된 **방법** (mock API / env 변수명). 크리덴셜을 파일·스크립트에 하드코딩 금지 — **저장되는 스크립트는 `process.env.{변수명}` 또는 프로젝트 mock 헬퍼 호출만** 포함해야 하며, 저장 전 크리덴셜 리터럴이 없는지 확인한다.
   - **캡처 전 게이트**: 로그인·온보딩·블로킹 모달이 기대 화면을 가리지 않는지 확인. 튜토리얼/웰컴/페이월 오버레이가 있으면 프로젝트 런북대로 dismiss하거나 **비튜토리얼 픽스처**로 교체한 뒤 진행. 가린 채로 찍은 스크린샷은 실패다.
   - 시드 데이터가 필요하면 **로컬 환경에서만** 만들고, **캡처 전에 픽스처가 의도대로인지 확인**한다. 화면이 픽스처와 모순되면 증거가 아니라 실패다. 만든 픽스처는 검증 후 정리한다 (불가하면 results에 명시).

4. **시나리오 실행 + 증거 캡처**:
   - **화면**: 시나리오별로 기대 결과를 화면에서 확인 → 지정 뷰포트로 캡처. 콘솔 에러/네트워크 실패도 함께 기록.
   - **로직**: 준비(픽스처 시드) → **실제 호출 실행** (curl/스크립트로 실제 엔드포인트에 요청, 또는 실제 명령 실행) → 기대와 대조 (상태 코드, 응답 필드 값, DB/로그 변화 — 시나리오의 구체적 기대값 기준) → 요청/응답 본문·로그 라인·DB 스냅샷을 `{run_dir}/verification/` 파일로 저장. **서버를 거치지 않는 함수 직접 호출·mock 클라이언트는 실행이 아니다.** 픽스처는 로컬 환경에서만 만들고 검증 후 정리한다 (§3 규칙 공유).
   - **막히면 전체 시나리오 타임아웃까지 기다리지 말고** 아래 **진단 사다리**를 탄 뒤 한 가지 원인만 고치고 재시도한다.
   - 스크립트는 가능하면 **재실행 가능**하게 남긴다 (일회성 수동 클릭·수동 curl만으로 검증 완료 금지 — 예외: 호스트 네이티브만 가능한 경우 notes에 절차 기록).

5. **S3 업로드 (화면 모드 전용 — 로직 증거는 텍스트라 업로드 없이 results/PR에 직접 넣는다)**
   - 설정: `~/.zen/config.json`의 `s3_bucket`, `s3_prefix`, `s3_region`, `public_url_prefix`, (선택) `object_acl`
   - config 부재·불완전이면 **추측 버킷에 업로드하지 않는다.** 로컬 경로 + `upload_failed: true` + “config 필요 필드” 목록을 results/PR에 명시.
   - **업로드 전 점검 (모든 스크린샷, 특히 실패분)**: 이메일/실명/토큰/API 키/스택트레이스/내부 URL이 화면에 있는지 확인 — 발견되면 마스킹 후 업로드, 마스킹 불가하면 업로드하지 않고 로컬 경로로만 보고. 업로드되는 모든 이미지는 공개 인터넷에 노출된다는 전제로 취급한다.
   - 업로드:
     ```bash
     # object_acl이 public-read 이면 (버킷 정책 없이 객체 ACL로 공개 읽을 때 — ObjectOwnership=ObjectWriter 필요)
     aws s3 cp {shot}.png "s3://{s3_bucket}/{s3_prefix}/{repo}/{branch-slug}/{scenario-slug}-{UTC}-{랜덤8}.png" \
       --region {s3_region} --content-type image/png --acl public-read
     # 버킷 정책으로 GetObject 공개면 --acl 생략 가능 (BucketOwnerEnforced)
     ```
     **키에 랜덤 토큰 필수** (URL 추측 방지). **버킷 ACL을 public-read로 열지 말 것** (ListBucket 노출). 객체 단위 공개만.
   - URL: `{public_url_prefix}/{key}` (prefix 미설정 시 `https://{bucket}.s3.{region}.amazonaws.com/{key}`)
   - 업로드 직후 **비인증** `curl -sI {url}` → **200** 확인. 403이면 ACL/버킷 정책 문제 — pass URL로 쓰지 말 것.
   - **presigned URL 금지** — 최대 7일 만료로 PR 기록이 깨진다.
   - **업로드 실패는 시나리오 pass 판정과 분리한다**: 1회 재시도 후에도 실패하면 로컬 경로를 results에 기록하고 `upload_failed: true` 표시 — zen은 이를 환경 예외(질문 허용, verify_attempts 미소모)로 승격한다. **단, 시나리오 자체 pass는 스크린샷이 기대를 보여줄 때만.**

6. **결과 산출**: `{run_dir}/verification/results.json`

   ```json
   {"commit": "abc1234", "base_url": "http://localhost:3000",
    "scenarios": [
     {"name": "인용 팝업 열림", "type": "screen", "viewport": "pc", "pass": true, "url": "https://…png", "notes": "콘솔 에러 없음"},
     {"name": "팝업 모바일 표시", "type": "screen", "viewport": "mobile", "pass": true, "url": "https://…png", "notes": ""},
     {"name": "인용 저장 API", "type": "logic", "pass": false, "evidence": "verification/quote-api.log",
      "notes": "실패 사유: 201 기대, 500 응답. 서버 로그에 FK 제약 위반"}
   ], "overall_pass": false}
   ```

   PR 바디용 마크다운 표도 함께 생성 — 화면은 이미지, 로직은 기대/실제 요약 + `<details>`에 요청/응답 본문:

   ```markdown
   | 시나리오 | 결과 | 증거 |
   |---|---|---|
   | 인용 팝업 열림 (PC) | ✅ | ![인용 팝업](https://…png) |
   | 인용 저장 API | ✅ | `POST /api/quotes` → 201, id 반환 (상세는 아래 접기) |
   ```

   로직 증거의 요청/응답 본문에 토큰·크리덴셜·개인정보가 있으면 마스킹 후 게시한다 (S3 업로드 전 점검과 동일 기준 — PR은 공개 기록이다).

## 실패 판정

- 기대 결과 불일치, 빈 화면/로딩 상태만 캡처됨, 관련 콘솔 에러 → 해당 시나리오 `pass: false` + 사유. 실패 스크린샷도 업로드한다 (디버깅 증거).
- **로직**: 기대 응답과 불일치(상태 코드·필드 값), 에러 응답/스택트레이스, 기대한 DB/로그 변화 부재 → `pass: false` + 실제 응답 첨부. **기대값 대조 없이 "호출이 에러 없이 끝남"만으로 pass 금지** — 시나리오의 구체적 기대값과 대조해야 한다.
- **증거 품질 게이트 (pass 전에 시각 확인)**: 스크린샷에 시나리오 핵심 UI(제목/본문/대상 버튼/상태 변화)가 **식별 가능**해야 한다. DOM assert만 통과하고 캡처가 흰 화면·0% 로딩·가린 오버레이·엉뚱한 탭이면 `pass: false` (또는 재캡처). “테스트는 녹색, 사진은 무관”은 실패다.
- zen 파이프라인 안에서는 `overall_pass: false`가 zen Phase 5의 조건부 수정 루프를 트리거한다 (경미한 수정 → 재검증만 / 구조적 수정 → 하네스 수렴 모드 1라운드 후 재검증 — 판정과 상한은 zen 본문). 단독 호출이면 실패 시나리오와 사유를 보고하고 종료한다 (임의로 수정에 들어가지 않는다).

## 진단 사다리 (로딩/로그인/인터랙션 실패 시)

한 번에 한 층만 확인하고, 실패 스크린샷 + console/network 한 줄 요약을 notes에 남긴다.

| 증상 | 먼저 볼 것 | 흔한 조치 |
|---|---|---|
| 빈 화면 / 앱 미마운트 | base URL, 서버 프로세스, 빌드 산출물 경로 | 서버 재기동, 올바른 build dir |
| 로그인·가입 화면이 계속 뜸 | 쿠키 도메인 vs API origin, mock 엔드포인트 활성(`PRODUCTION` 등), extension이 **prod API**를 치는지 | **development 빌드**(localhost API), mock sign-up 헬퍼 |
| 스피너 0% / 에셋 미로드 | `requestfailed` / `ERR_FILE_NOT_FOUND`, worker·wasm·pdf.js 경로 | 누락 자산 복구/재빌드, public 정적 파일 확인 |
| 클릭·선택이 안 됨 | 블로킹 모달(온보딩/튜토리얼/쿠키/페이월), `pointer-events`, iframe 포커스 | dismiss 또는 **비튜토리얼 픽스처**, iframe 좌표로 드래그 |
| 팝업 셀렉터 0건 | 숨은 템플릿 DOM vs `:visible`, selection 제스처 | visible 필터, 긴 텍스트 가로 드래그, 기존 e2e와 동일 제스처 |
| 타임아웃만 반복 | 위 층을 건너뛰고 시나리오만 재실행 중인지 | 진단 없이 240s 재실행 금지 — 층별 스모크 후 재시도 |

## 흔한 실수

- 스크린샷에 실계정 정보 노출 → 테스트 계정만 사용. 시나리오에 마스킹 대상이 명시돼 있으면 CSS로 가리고 캡처.
- dev 서버를 새로 띄우고 방치 → 검증 후 **자기가 띄운 서버만** 종료한다 (원래 떠 있던 것은 유지).
- 로딩 완료를 기다리지 않고 캡처 → 명시적 대기 조건(요소 표시, 네트워크 idle)을 쓴다. sleep 고정값 금지.
- **브라우저/서버를 안 띄우고 단위 테스트 결과만 results.json에 넣어 pass 처리** → 금지. 이 스킬의 산출물은 실환경 재현 증거(스크린샷·실제 응답)다. 환경이 없으면 실행을 중단·보고하고, zen 파이프라인이면 예외 5로 인계한다 (단위 테스트 우회 완료 금지).
- **로직 검증을 함수 직접 호출·mock 클라이언트·테스트 러너로 대체** → 금지. 실제 떠 있는 서버 프로세스에 실제 요청이 나가야 실환경 재현이다.
- **모바일 지정 시나리오를 PC 캡처로 대체** → 금지. 390x844(가능하면 디바이스 에뮬레이션)로 캡처한다.
- **환경 문제를 제품 버그로 3회 소진** → 금지. 로그인/에셋/서버 이슈는 진단 사다리 + 예외 5.
- **prod 빌드 extension + localhost 쿠키** 혼용 → 세션 불일치. surface 런북의 빌드 모드를 따른다.
- **튜토리얼/웰컴 픽스처로 본 기능 검증** → 블로킹 모달에 가려짐. 비튜토리얼 PDF/페이지 사용.
- S3 버킷을 기억·추측으로 업로드 → 금지. config에 있는 값만 사용.
